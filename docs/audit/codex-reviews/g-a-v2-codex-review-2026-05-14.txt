## §0. Bottom-line recommendation
hold-and-rework

Reason: the G.A-v2 idea is directionally useful, but the v1.1 spec is not file-ready. The main blockers are: required reference documents are missing from the checkout; the spec has no per-ticket boundaries / required paths even though the review prompt and G.A-v1 precedent require those at filing quality; several integration tickets are tier:S despite being integration / soak / migration gates; the SD-1 dog-food rule is introduced without evidence blocks for the spec's own novelty-style claims; and multiple recovery / rescue paths remain operator-shaped rather than deterministic enough to file.

## §2. P1 STRUCTURAL findings (should fix in v2)

### P1-1 — Family ⑥ D4/D5 recovery is not deterministic enough for the highest-priority outage class

Evidence:
- Option C says image-ahead auto-runs `alembic upgrade head`; image-behind exits 78 with remediation (`docs/sprint-s12/sprint-s12g-A-v2-runtime-defense-contract-spec.md:190-198`).
- The retrospective identifies real drift candidates beyond simple image-vs-DB version skew: manual `alembic upgrade head` from dev workspace, cross-branch head merge, or previous rollback leaving DB ahead (`docs/retrospectives/2026-05-14-host-reboot-image-db-drift.md:162-170`).
- `v2-⑥-RescueCLI` bundles DB downgrade with backup, manual upgrade with override, and L2 fingerprint into one ticket (`docs/sprint-s12/sprint-s12g-A-v2-runtime-defense-contract-spec.md:209`).

Gap: the spec does not define how the startup hook handles multi-heads, branch labels, failed partial migrations, data-destructive downgrades, or advisory locking between two backend replicas starting concurrently.

Concrete fix: split Family ⑥ into deterministic subcontracts: migration lock/acquire semantics; image-head resolution algorithm; forward startup hook; backward fail-fast; rescue backup capture; downgrade eligibility matrix; override/audit event writer. Make `v2-⑥-RescueCLI` tier:M/L and require an explicit no-downgrade-default path.

### P1-2 — Family ⑤ misses the consumer-side auto-pull / auto-redeploy gap from the retrospective

Evidence:
- Retrospective gap #2 says OP-1035 only added the build side; the consumer side does not exist, with options such as `pull_policy: always`, cron redeploy, Watchtower / Diun / custom watcher (`docs/retrospectives/2026-05-14-host-reboot-image-db-drift.md:106-114`).
- The v2 spec Family ⑤ covers `/version`, manifest bake, deployment-audit script, timer, alert rule, and integration (`docs/sprint-s12/sprint-s12g-A-v2-runtime-defense-contract-spec.md:216-232`).
- The spec explicitly scopes Family ⑤ to detection/remediation and says D3/D4/D5 are N/A (`docs/sprint-s12/sprint-s12g-A-v2-runtime-defense-contract-spec.md:220`).

Gap: detection catches stale images, but no ticket closes the missing consumer redeploy path. If the audit fires daily, recovery is still manual and timing-dependent.

Concrete fix: either add a D4 remediation ticket for `pull latest + recreate + verify /readyz`, or explicitly state that Family ⑤ only detects and files a follow-up blocker for 31.H/31.J/31.E to own auto-redeploy. Without that, ⑤ is incomplete against the retro.

### P1-3 — Family ⑦ fixes allowlist drift but not the enforce-mode rollout ambiguity named in the retro

Evidence:
- Retrospective says `/health` 401 may be caused by a third enforcement point or out-of-sync enforcement layer in `auth_baseline.py` enforce mode (`docs/retrospectives/2026-05-14-host-reboot-image-db-drift.md:177-183`).
- Spec chooses single-source allowlist consumed by five middleware and then resolves `/health` path policy (`docs/sprint-s12/sprint-s12g-A-v2-runtime-defense-contract-spec.md:240-257`).
- Spec defers full auth strict-mode rollout audit (`docs/sprint-s12/sprint-s12g-A-v2-runtime-defense-contract-spec.md:397-400`).

Gap: the family may prove all five listed middleware call `is_public()`, but still miss hidden auth surfaces, mount-order behavior, reverse-proxy health path differences, or `/api/v1/health` vs `/health` split.

Concrete fix: add one discovery/audit ticket before `v2-⑦-2bc` that enumerates every auth decision point and its middleware order. Require a failing test reproducing current `/health` 401 before refactor. If full auth audit is deferred, explicitly define the subset that this family certifies.

### P1-4 — Family ⑧ underestimates host-side WSL2 shutdown limits and labels D1/D2/D5 as partial without tickets

Evidence:
- Retrospective says WSL2 emitted `RB_POWER_OFF` after 10,000 ms and `user@1000.service` default `TimeoutStopSec` is 30s (`docs/retrospectives/2026-05-14-host-reboot-image-db-drift.md:17-25`, `184-192`).
- Spec says Productizer-internal only; Windows-side hooks are out of scope (`docs/sprint-s12/sprint-s12g-A-v2-runtime-defense-contract-spec.md:49-53`).
- Family ⑧ says D1/D2/D5 are partial, but the ticket table only implements D3/D4 (`docs/sprint-s12/sprint-s12g-A-v2-runtime-defense-contract-spec.md:263-276`).

Gap: increasing systemd `TimeoutStopSec` and compose `stop_grace_period` may not beat the Windows / WSL hard shutdown path that killed the instance. There is also no D1 signal for "last shutdown was forced" or D2 remediation for post-reboot warning.

Concrete fix: either mark D1/D2/D5 N/A with rationale, or add explicit tickets for post-boot forced-shutdown detection, operator warning, and rescue escalation. Add a hard assumption test proving WSL honors the proposed systemd path during Windows update shutdown.

### P1-5 — Family ⑨ changes from cross-project hygiene to optional auxiliary contract but leaves daemon hygiene only as a one-shot decision

Evidence:
- Retrospective says `ai_gateway` has been crashlooping for 10 days and the cross-project hygiene gap is uncontracted (`docs/retrospectives/2026-05-14-host-reboot-image-db-drift.md:194-199`).
- Spec reframes ai-core as optional auxiliary and limits broader cross-project policy to post-rc2 (`docs/sprint-s12/sprint-s12g-A-v2-runtime-defense-contract-spec.md:278-288`, `397-402`).
- `v2-⑨-3a-Decision` is a one-shot operator decision about the current crashlooping container and says it does not affect the contract (`docs/sprint-s12/sprint-s12g-A-v2-runtime-defense-contract-spec.md:297`).

Gap: the spec makes application fallback dynamic, but does not prevent the original host-level resource problem from recurring for another optional stack. The root incident included daemon/log/CPU hygiene, not just Productizer provider-chain behavior.

Concrete fix: add a minimal D1 host hygiene signal scoped to known auxiliary containers, or explicitly split this into a separate post-rc2 META with a blocker relationship. The current `v2-⑨-3a-Decision` should not be counted as closing the retro gap.

### P1-6 — `v2-A3` is too coarse for tier:S if it includes field validators, cross-field validators, SD interactions, and bootstrap exclusions

Evidence:
- §2 defines 5 dimensions with many subfields and enums (`docs/sprint-s12/sprint-s12g-A-v2-runtime-defense-contract-spec.md:56-100`).
- §2 lists six runtime forbidden combinations (`102-113`).
- §4 has `v2-A3` as "defense_contract field-level validators" tier:S, and `v2-A9` later adds SD-1 validator tier:S (`306-314`).

Gap: the field validators are not just shape checks; they interact with runtime capability, destructive op classes, lifecycle detection, user-facing remediation, and rescue semantics. If A3 owns all field-level validators, it will need several fixture classes and existing payload compatibility handling.

Concrete fix: split A3 into `A3a schema field validators`, `A3b runtime cross-field forbidden combinations`, and `A3c bootstrap/audit-mode compatibility`, or make A3 tier:M with detailed fixtures.

### P1-7 — AlertBridge framework promises "zero-surprise swap" and byte-for-byte equivalence before knowing 31.G's actual AM payload contract

Evidence:
- AlertBridge says the AM bridge migration is a config change and no rule changes (`docs/sprint-s12/sprint-s12g-A-v2-runtime-defense-contract-spec.md:167-180`).
- `v2-AlertBridge-AMMigrationTest` requires `P == P'` byte-for-byte modulo timestamps (`178`).
- Cross-phase dependencies say 31.G-LibsGate blocks v2 alert rules because Prometheus + AM stack is needed (`352-354`).

Gap: stdout/email and AM webhook payloads are unlikely to be byte-identical if AM injects grouping, receiver, status, fingerprint, startsAt/endsAt, generatorURL, or labels. The framework can preserve a canonical normalized event, but byte-for-byte AM equality is likely the wrong invariant.

Concrete fix: define a canonical alert envelope and compare normalized fields, not transport payload bytes. Change the dependency wording so AlertBridge contract can be filed before 31.G, but AM migration test is blocked by the concrete 31.G receiver schema.
