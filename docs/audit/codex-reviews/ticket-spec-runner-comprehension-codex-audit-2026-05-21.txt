## A. Title comprehension and tag correctness

### Global title/tag finding

A cold runner will not receive enough scope from many titles as currently written. The spec explicitly says each row must expand into a full Story with Prerequisites YAML, 4 AC sections, Go-Live, and executable `verify:` blocks before POST (`docs/design/2026-05-21-release-train-ticket-spec.md:15-16`), but the current table mostly provides only compact titles, broad areas, and one key AC phrase (`docs/design/2026-05-21-release-train-ticket-spec.md:32-94`). That is not inherently wrong for a blueprint, but it means the table itself is not runner-comprehensible enough without the filing expansion.

The action-tag convention is coherent: `[BOT]` means Story + `class:subscription-*` + `agent:auto`, `[OP]` is fallback/operator work, `[GATE]` is narrow approval-only, `[HOLD]` means blocked, and integration/test Stories are explicitly corrected to `[BOT]` (`docs/design/2026-05-21-release-train-ticket-spec.md:23-25`). However, the table's `labels` column for BOT rows only shows `capability:enable=gerrit_push`, while line 25 says all `[BOT]` rows also carry `agent:auto` + `class:subscription-*`; filing must materialize those labels, because title-only tags are not runner routing metadata.

Runtime reality: runner pickup JQL filters `issuetype = Story`, `status = To Do`, empty assignee, exact `class:<runner_class>`, and excludes `tier:X`; it does not require `agent:auto` (`backend/agents/jira_dispatch.py:357-365`). `scripts/file_jira_ticket.py` has the same pickup JQL shape (`scripts/file_jira_ticket.py:112-122`). So `[BOT]` correctness matters to humans, but the real pickup gate is labels/type/tier. A misfiled `[OP]` with `class:subscription-*` and non-X tier could still be picked unless `tier:X`/operator refusal labels prevent it.

## C. Scope-anchor sufficiency

### Global insufficiency

The spec claims “Scope-anchor (Goal + Files + Spec-ref to this doc) is present” (`docs/design/2026-05-21-release-train-ticket-spec.md:15-16`), but the table does not actually contain per-ticket `Goal`, concrete `Files / Paths`, or precise section-level `Spec-ref` fields. The runner machinery depends on the description’s explicit `Files / Paths` section for file-level mutex prediction (`backend/agents/jira_dispatch.py:2137-2158`), and the parser only extracts concrete file tokens under a `Files / Paths` heading (`backend/agents/scope_to_paths.py:60-85`). If filing expansion does not add those sections, the runner falls back to always-touched/per-scope defaults, which are too coarse or empty (`backend/agents/jira_dispatch.py:2143-2165`).

Runner prompt boundaries are area-based. `_build_prompt` injects declared areas, a forbidden area list, and tells the agent to halt on out-of-area work (`auto-runner-jira.py:1106-1118`, `auto-runner-jira.py:1186-1200`). The SOP says area labels become goal anchors through that negation list (`docs/sop/jira-ticket-conventions.md:170-195`), and the filing checklist says areas must span every 4-AC directory (`docs/sop/runner-ticket-filing-checklist.md:63-69`). Therefore each expanded Story must include concrete files and correct area union, or the runner will either stop mid-ticket or over-edit.

### Tickets with adequate anchor candidates in the row

- RT-03: Row lists exact files: `auto-runner-jira.py`, `scripts/file_jira_ticket.py`, schema/conventions docs, capability matrix, tests (`docs/design/2026-05-21-release-train-ticket-spec.md:36`). This is the strongest current scope anchor.
- RT-23: Row names `webhooks.py` in AC, but should expand to `backend/routers/webhooks.py` plus tests (`docs/design/2026-05-21-release-train-ticket-spec.md:38`).
- RT-07a/RT-07b: Titles name `deploy-prod.sh`, `check_deploy_ref.sh`, allowlist, prod compose (`docs/design/2026-05-21-release-train-ticket-spec.md:65-67`). These should expand to exact paths.
- RT-12: Title and intent point to `scripts/promote_image_bundle.py` / GitLab CR / three-image digest verify; but it still needs exact file list from Model A change points (`docs/design/2026-05-21-model-a-candidate-build-release-train.md:73-84`).
- RT-15a/15b: Titles imply backend router + FE provider/hook; exact files not present.

### Tickets where a runner will not know which files to edit

- RT-04a/04b/04d/04e: No exact CI config/test/store files. RT-04a likely `.gitlab-ci.yml`/Gerrit integration; RT-04b likely DB/backend; RT-04d/04e tests. The spec does not say.
- RT-05a/05b/05c/05d/05e: Some titles imply files (`deploy/staging/docker-compose.yml`, `scripts/sync_staging_to_develop.sh`, `backend/frontend_compat.py`, `scripts/staging_gate.py`, `backend/api_versioning.py`), but none are in the spec row.
- RT-06: No exact verifier/doc/audit files; could touch `.gitlab-ci.yml`, `scripts/verify_image_signature.sh` if present, audit JSON generation, docs.
- RT-08: No exact API version/readyz files. Existing candidates include `backend/api_versioning.py` and readyz tests, but spec does not anchor.
- RT-09: No exact CI/API files; hidden choice risk around pipeline API vs GitLab YAML.
- RT-10a/10b/10c: No exact model/migration/service/test files for new `release_train` table.
- RT-11/RT-22/RT-14: No exact modules; title names concepts, not paths.
- RT-13a: New tool path is clear (`release_train_status.py`) but module location is not specified (`scripts/` vs `backend/agents/` vs package entrypoint).
- RT-16/17: Operator runbooks need explicit command checklist/files; title alone is insufficient.

Recommended filing format: every RT Story description must include:

```
## Goal
One sentence, imperative, explicitly excluding sibling work.

## Files / Paths
- exact/path.ext
- exact/test_path.ext

## Spec references
- docs/design/2026-05-21-release-train-ticket-spec.md:RT-NN row
- docs/design/2026-05-21-release-train-workplan.md:<specific phase lines>
- docs/design/2026-05-21-model-a-candidate-build-release-train.md:<specific corrected rule lines>

## Out of scope
- RT-XX sibling owns ...
```

This matches the filing checklist’s `Files / Paths` and spec references template (`docs/sop/runner-ticket-filing-checklist.md:130-145`) and the decomposition template that each child must have scope, 4-AC, decision points, verify blocks, dependencies (`docs/sop/sprint-s12-ticket-decomposition-rules.md:460-483`).

## D. Cross-ticket confusion, collisions, and mutex needs

### Collision classes

- Filing/tooling collision: RT-03 touches runner/file-ticket/schema/capability files. It must land before filing ci/gerrit/db tickets per hard filing order (`docs/design/2026-05-21-release-train-ticket-spec.md:18-19`). Mutex: `mutex:rt-filing-vocab` for RT-03 only; hold all ci/gerrit/db rows until merged.

- Webhook/runtime freeze collision: RT-01 runtime disables old writers; RT-23 edits `backend/routers/webhooks.py`. RT-23 is correctly blocked by RT-01 (`docs/design/2026-05-21-release-train-ticket-spec.md:38`, `docs/design/2026-05-21-release-train-ticket-spec.md:99`).
