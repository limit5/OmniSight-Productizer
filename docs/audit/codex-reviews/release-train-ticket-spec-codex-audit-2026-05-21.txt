# Release-train ticket spec audit — Codex / GPT-5.5

Date: 2026-05-21
Target: docs/design/2026-05-21-release-train-ticket-spec.md
Prompt: docs/codex-review-prompts/2026-05-21-release-train-ticket-spec-audit-prompt.md

Verdict: GO-WITH-FIXES, not clean GO. The spec is directionally much better than the v1 work plan: the P1.4-before-P1.5 ordering bug is gone, the v1 P0.6/P1.3 cycle is gone, and most of the prior must-fixes are represented as RT tickets. However, it is not yet safe to file as-is. The biggest blockers are filing-correctness problems, not release-model problems: the spec is a summary table, but the filing SOP requires per-Story descriptions with Prerequisites YAML, exact labels, four AC sections, machine-executable verify blocks, and area labels spanning all touched paths. Several RT rows also use unresolved labels such as `ci(or devops)` / `gerrit(or devops)`, missing exact `runner:no-commits-expected` labels, unsupported/ambiguous `type` values, and areas that today's filing script or runner cannot accept.

## D. Capability / Tier / Type Correctness

D1. BLOCKER — missing `class:*` on every row.

JIRA conventions require Class, Tier, and Area labels on every ticket (docs/sop/jira-ticket-conventions.md:70-76), and label conventions explain class drives runner JQL pickup (docs/sop/jira-label-conventions.md:68-77). The ticket spec has tier/type/areas/caps but no `class` column or per-ticket class decision (docs/design/2026-05-21-release-train-ticket-spec.md:15-20). This matters because file_jira_ticket requires `--class` (scripts/file_jira_ticket.py:274-286).

D2. BLOCKER — `caps` shorthand is not exact labels.

Rows use `gerrit_push` and `no-commits` shorthand (docs/design/2026-05-21-release-train-ticket-spec.md:18-20,26-30,68-69). The actual capability override label form is `capability:enable=<cap>` (docs/sop/jira-label-conventions.md:86-95; docs/sop/jira-label-schema.yaml:63-76), and the ops-only label is `runner:no-commits-expected` (docs/sop/jira-ticket-conventions.md:1331-1340). D3. BLOCKER — several type values are not file_jira_ticket-compatible and/or are unsafe.

`file_jira_ticket.py` supports `--type bug|feature|docs|meta` (scripts/file_jira_ticket.py:274-286). The spec uses `type:meta-doc`, `ops`, `meta·tier:X`, `Story·tier:X·ops`, etc. (docs/design/2026-05-21-release-train-ticket-spec.md:17-18,25,35,42,60,68-69). Fix: normalize to CLI-supported types or update the CLI/schema/tests first. Parent rows with children can use `type:meta`; implementation/ops/doc rows should use `type:feature`, `type:docs`, or another validated type only after tooling supports it.

D4. BLOCKER — tier:X + runner class/capability needs precise handling.

The filing checklist says tier:X is human-only and runner JQL excludes tier:X (docs/sop/runner-ticket-filing-checklist.md:47-54). The spec currently labels some as `[OP]`/`[GATE]`, but still uses Story rows and caps shorthand (docs/design/2026-05-21-release-train-ticket-spec.md:17-18,68-69). D5. MED — tier:S RT-04d has `gerrit_push` but tier:S may not need or permit full integration scope.

## F. Filing-Time Hazards

F1. BLOCKER — filing all tickets in one batch before RT-03 lands will create unknown-area / invalid-area loops.

The spec explicitly says `ci`/`gerrit` are not yet recognized and points to RT-03 (docs/design/2026-05-21-release-train-ticket-spec.md:5,93). The runner will raise UnknownAreaLabelError on unknown areas (auto-runner-jira.py:153-159,1107-1110). The filing checklist says unknown area labels can cause pickup/revert loops (docs/sop/runner-ticket-filing-checklist.md:40-45,194-199). Therefore do not batch-file RT-04a/04c/09/17 with `area:ci`/`area:gerrit` until RT-03 is published, or file them as HOLD/no class and relabel after RT-03.

F2. BLOCKER — file_jira_ticket.py currently conflicts with the canonical area set.

Current `file_jira_ticket.py` accepts `gerrit` but not `ci`, and rejects `db` as a runner-only area even though runner/schema include db (scripts/file_jira_ticket.py:37-47,62-66,184-193; auto-runner-jira.py:147-150; docs/sop/jira-label-schema.yaml:53-59). This means RT-04b/10a/11 with db cannot be filed via the standard script, while `gerrit` could be filed but then fail runner/schema. RT-03 must correct this drift before filing dependent tickets.

F3. BLOCKER — parent META rows with area `—` violate required labels if filed as Stories.

Every ticket requires area labels (docs/sop/jira-ticket-conventions.md:70-76). Parent rows RT-04/05/07/10/15 use `areas —` (docs/design/2026-05-21-release-train-ticket-spec.md:25,35,42,52,60). If these are actual JIRA Stories, they need at least area:docs/tooling or a validated Epic/META filing path. Empty area is not allowed by capability resolution, which requires at least one area for multi-area resolve (backend/agents/capability_matrix.py:210-231). Fix parent filing format.

F4. BLOCKER — no exact `runner:no-commits-expected` labels on ops-only rows.

Rows use caps `no-commits` (docs/design/2026-05-21-release-train-ticket-spec.md:18,68-69). The real label is `runner:no-commits-expected` (docs/sop/jira-ticket-conventions.md:1331-1340), and the runner prompt-builder/zero-commit path key off that exact label (docs/sop/jira-ticket-conventions.md:1344-1363; auto-runner-jira.py:1155-1164). Fix every ops-only ticket to use the exact label or no class/tier:X operator handling.

F5. BLOCKER — coord-override labels need operator approval/comments.

Capability overrides and `runner:no-commits-expected` change execution semantics; the schema marks `capability:*` as coord_override and `runner:no-commits-expected` as coord_override_adjacent (docs/sop/jira-label-schema.yaml:63-76,154-160). Label conventions say capability overrides are operator-gated (docs/sop/jira-label-conventions.md:86-95). If a filing script auto-adds `capability:enable=gerrit_push`, that is fine for default subscription tickets, but non-default capability changes and ops-only labels should be explicitly operator-approved in the ticket body/comment.

F6. BLOCKER — no Prerequisites YAML means dependency graph may exist only as table prose, not runner-readable metadata.

JIRA conventions require `## Prerequisites` YAML in every Story description (docs/sop/jira-ticket-conventions.md:284-299). The table has a `blockedBy` column, but the actual ticket descriptions must include blocks_on and the filing/wire script must create Blocks links in the correct direction. Without that, scheduler/live-state enforcement can miss blockers (docs/sop/jira-ticket-conventions.md:397-406).

F7. MED — summary prefix discipline is stated globally but not normalized per ticket.

The spec says 6-tag prefix discipline applies (docs/design/2026-05-21-release-train-ticket-spec.md:5), but some rows have `[BOT+OP]`, `[META]`, `[GATE]`, `[OP]` (docs/design/2026-05-21-release-train-ticket-spec.md:51,52,68-69). `[BOT+OP]` is not one of `[BOT/OP/META/REF/GATE/HOLD]`; split it instead. RT-13 is the main offender.
