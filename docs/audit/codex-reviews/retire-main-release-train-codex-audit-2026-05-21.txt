Retire main / tag-driven release train audit
Date: 2026-05-21
Reviewer: Codex / GPT-5.5
Scope: docs/codex-review-prompts/2026-05-21-retire-main-release-train-audit-prompt.md

Executive stance

The proposed direction is coherent only if it is implemented as a true model change, not as a search-and-replace from main to develop. The current tree still has multiple independently active definitions of “release”: Gerrit main fast-forward, release/vX.Y branch maintenance, deploy-by-branch, staging-by-develop-SHA, and v* tag image publication. Those can coexist only because the present system is transitional. Once main is retired, they become correctness hazards.

Highest-risk net-new findings:

1. Staging currently deploys the raw develop commit SHA, but the GitLab image pipeline only runs for v* tags and publishes sha-${CI_COMMIT_SHORT_SHA}, not a raw full-SHA image. A tag-only train must resolve this build/staging circular dependency before auto-cutting tags.
2. The production deploy allowlist still permits main, release/*, and hotfix/* branch deploys; this is separate from deploy-prod.sh’s main default and must be changed atomically with deploy script changes.
3. The GitLab release pipeline claims keyless/OIDC attestation in emitted audit JSON and docs, but the job signs with COSIGN_KEY and no id_tokens are present. That weakens the supply-chain story for “every tag is prod-usable.”
4. The baked bundle.json in images is generated before image digests exist, so /api/version cannot prove the final image digest closure without a post-build re-seal or separate trusted bundle artifact.
5. A pure “tag only from develop” hotfix cannot isolate a production fix if develop already contains unshippable changes. The plan needs an explicit stop-the-line/revert policy or a tightly defined exception, otherwise “v0.6.1 hotfix from develop” silently means “ship every later develop commit too.”

A. Additional main/release/* couplings and obsolete components

A1. NET-NEW, HIGH, MODIFY: staging-sync expects raw develop-SHA images that the tag-only GitLab pipeline does not build.

Evidence:
- scripts/sync_staging_to_develop.sh documents that staging should deploy “the image tagged with that commit SHA” from develop: scripts/sync_staging_to_develop.sh:16-scripts/sync_staging_to_develop.sh:23.
- It resolves the develop tip via Gerrit fetch and rev-parse: scripts/sync_staging_to_develop.sh:178-scripts/sync_staging_to_develop.sh:193.
- It deploys OMNISIGHT_IMAGE_TAG=${develop_tip}: scripts/sync_staging_to_develop.sh:255-scripts/sync_staging_to_develop.sh:270.
- The GitLab pipeline runs only for v* tags: .gitlab-ci.yml:1-.gitlab-ci.yml:4.
- The release pipeline pushes ${CI_COMMIT_TAG}, sha-${CI_COMMIT_SHORT_SHA}, and latest, not the raw full develop SHA used by staging-sync: .gitlab-ci.yml:118-.gitlab-ci.yml:120.

Impact:
Under the new model, the scheduler needs staging to prove develop is green before creating the v* tag, but the current staging-sync path expects an image tag that the tag pipeline will not create until after a v* tag exists. That is a release-train circular dependency.

Required action:
Decide the candidate artifact model before retiring main. Either build immutable candidate images for every accepted develop commit, change staging-sync to deploy sha-${short_sha} from a branch pipeline, or auto-create a pre-release candidate tag and stage that exact tag before promoting to a final v* tag. Do not rely on raw develop SHA image tags unless the build pipeline actually publishes them.

Evidence:

B. Hidden costs of “pure tag on develop” releases

B1. NET-NEW, HIGH, NEW-WORK: hotfixes cannot isolate a production fix if develop already contains unshippable commits.

Evidence:
- ADR-0001’s problem statement explicitly calls out emergency hotfixes conflicting with in-progress development: docs/adr/ADR-0001-five-branch-gitflow.md:25-docs/adr/ADR-0001-five-branch-gitflow.md:33.
- The old model solved this by making hotfix/* branch from main and merge back: docs/adr/ADR-0001-five-branch-gitflow.md:53-docs/adr/ADR-0001-five-branch-gitflow.md:54.
- The new plan removes hotfix branches and says hotfix tags are also from develop.

Impact:
If develop has commits after the last production tag that are not prod-ready, a hotfix tag from develop necessarily ships them. This is the largest semantic cost of the new model.

Required action:
Define a stop-the-line rule: either revert or disable unready develop changes before tagging, or explicitly permit a temporary detached/tag-only hotfix process from the last production tag. If the latter is rejected, the revert policy and owner approval need to be written down before retiring hotfix branches.

B2. NET-NEW, HIGH, NEW-WORK: “every tag is prod-usable” is not currently backed by required tests.

Evidence:
- .gitlab-ci.yml has only build/sign/sbom/attest/audit-emit stages, not test/lint: .gitlab-ci.yml:6-.gitlab-ci.yml:11.
- GitLab pipeline is tag-only: .gitlab-ci.yml:1-.gitlab-ci.yml:4.
- Gerrit Verified is disabled: .gerrit/project.config:312-.gerrit/project.config:315.
- staging-gate-smoke defaults to a narrow dag1 smoke id: deploy/systemd/staging-gate-smoke.service:30-deploy/systemd/staging-gate-smoke.service:39.
- release_milestone_checker gates canary and smoke status, but the status source is JSONL staging gate output, not a comprehensive CI test suite: scripts/release_milestone_checker.py:517-scripts/release_milestone_checker.py:531.

Impact:
A v* tag can currently build, sign, and emit attestations without proving the backend/frontend test suite passed at that commit. Tag immutability makes this more serious than branch releases because a bad tag becomes a permanent release object.

Required action:
Before unattended tag creation, require a fresh green signal for the exact develop commit. Minimum should include backend pytest via backend/.venv/bin/pytest for relevant suites, frontend build/typecheck/tests, migration check, smoke/canary, and supply-chain verification.

B3. NET-NEW, HIGH, NEW-WORK: rollback cannot assume tag-only deploy is enough when database migrations have already run.

Evidence:
- deploy-prod.sh runs Alembic migration upgrade during deployment: scripts/deploy-prod.sh:330-scripts/deploy-prod.sh:378.
- Its rollback guidance is “checkout previous tag, rerun deploy-prod.sh --skip-build”: scripts/deploy-prod.sh:469-scripts/deploy-prod.sh:471.
- release state machine supports rollback only from canary stages, not from done: backend/release_conductor/state_machine.py:24-backend/release_conductor/state_machine.py:37, backend/release_conductor/state_machine.py:100-backend/release_conductor/state_machine.py:130.

Impact:
Pure tag rollback does not undo schema changes. A production-usable-tag policy must include backward-compatible migrations or explicit downgrade/restore procedures.

Required action:
Add a release gate that classifies migrations as backward-compatible, requires expand/contract sequencing, or blocks tag cut. Rollback docs should say exactly when previous-tag deploy is valid and when DB intervention is required.

B4. NET-NEW, MEDIUM, MODIFY: “force promote” semantics become unsafe in a no-branch tag model.

Evidence:
- release_milestone_checker has FORCE_PROMOTE handling that can bypass milestone readiness blockers: scripts/release_milestone_checker.py:540-scripts/release_milestone_checker.py:549.
- The old auto-promote script treats milestone ready as permission to push refs/for/main: scripts/auto_promote_develop_to_main.sh:16-scripts/auto_promote_develop_to_main.sh:21.

Impact:
In the old model, force-promote still created a Gerrit main change for review. In the tag model, a force path could create a production release tag directly if copied naively.

Required action:
Remove force from unattended auto-cut. If an emergency override remains, require explicit human invocation, immutable audit reason, exact commit SHA, and post-tag verification.

E. Supply-chain and image-release considerations

E1. NET-NEW, HIGH, MODIFY: signing/attestation mode is internally inconsistent.

Evidence:
- sign-images uses cosign sign --key "$COSIGN_KEY": .gitlab-ci.yml:137-.gitlab-ci.yml:151.
- attest-images also uses --key "$COSIGN_KEY": .gitlab-ci.yml:173-.gitlab-ci.yml:200.
- audit-emit records signed_with as cosign-keyless-gitlab-oidc: .gitlab-ci.yml:246-.gitlab-ci.yml:287.
- The release image pipeline doc claims keyless OIDC/id_tokens: docs/operations/release-image-pipeline.md:84-docs/operations/release-image-pipeline.md:106.

Impact:
Audit output can claim keyless identity guarantees that the pipeline did not actually use. For tag-only releases, that undermines the “immutable tag = prod-usable artifact” contract.

Required action:
Either implement GitLab OIDC keyless signing with id_tokens and Fulcio identity checks, or change docs/audit JSON to accurately say key-based signing and document key custody.

E2. NET-NEW, HIGH, MODIFY: image-baked bundle.json is generated before final image digests exist.

Evidence:
- prepare-bundle emits placeholder zero digests before build: .gitlab-ci.yml:63-.gitlab-ci.yml:75.
- Dockerfile.backend copies bundle.json into the runtime image: Dockerfile.backend:174-Dockerfile.backend:182.
- /api/version reads the bundled metadata exposed by backend/api_versioning.py: backend/api_versioning.py:254-backend/api_versioning.py:327.
- emit_bundle_json.sh supports real git_ref/git_sha/images/contracts fields: scripts/emit_bundle_json.sh:109-scripts/emit_bundle_json.sh:127.

Impact:
The running backend’s /api/version cannot, by itself, prove that it is serving the final image digests created later in the pipeline. A separate post-build bundle can be correct, but then operators must know the in-image bundle is not the final attestation source.

Required action:
Either re-seal/publish a final bundle after image build and teach deploy/health/audit to trust that external bundle, or restructure the build so final digest provenance is available to the runtime metadata path.

E3. NET-NEW, MEDIUM, MODIFY: mutable latest remains a deployment foot-gun.

Evidence:
- The GitLab pipeline pushes latest on every v* tag: .gitlab-ci.yml:118-.gitlab-ci.yml:120.
- docker-compose.prod.yml defaults OMNISIGHT_IMAGE_TAG to latest: docker-compose.prod.yml:33-docker-compose.prod.yml:35.
- The release image pipeline doc says latest is updated on every v* tag and production should pin digest for zero drift: docs/operations/release-image-pipeline.md:121-docs/operations/release-image-pipeline.md:124.

Impact:
If OMNISIGHT_IMAGE_TAG is unset in production, the stack can deploy the newest tag regardless of approval state. Under a tag train, latest should be convenience-only and never a default in prod/staging compose.

Required action:
Make production and staging fail if OMNISIGHT_IMAGE_TAG is unset. Keep latest only for local/manual inspection, or remove it from release publication.

E4. NET-NEW, MEDIUM, MODIFY: /api/version exposes bundle-level identity but not enough direct release-tag provenance for tag-first ops.

Evidence:
- build_version_payload returns bundle_id, API compatibility, OpenAPI hash, DB schema version, and provider chain metadata: backend/api_versioning.py:254-backend/api_versioning.py:327.
- bundle.json generation includes git_ref and git_sha: scripts/emit_bundle_json.sh:109-scripts/emit_bundle_json.sh:127.

Impact:
Operators debugging a tag-driven rollout should be able to ask a running service “which v* tag and commit are you?” without separately decoding bundle_id or looking up an external artifact.

Required action:
Expose git_ref/git_sha from bundle.json in /api/version, or document why bundle_id is the canonical lookup key and provide a deterministic lookup path.

E5. NET-NEW, MEDIUM, MODIFY: frontend/backend compatibility check is observational, not a release gate.

Evidence:
- docs/operations/release-image-pipeline.md says /readyz compares API support and catches incompatibility before traffic: docs/operations/release-image-pipeline.md:171-docs/operations/release-image-pipeline.md:182.
- backend/frontend_compat.py says its current policy is observational and never blocks readiness: backend/frontend_compat.py:24-backend/frontend_compat.py:31.
- health readyz computes ready from db, migrations, and provider chain only: backend/routers/health.py:577-backend/routers/health.py:674, especially backend/routers/health.py:663.

Impact:
The docs overstate the safety gate. Tag-only releases with frontend flags need a real compatibility gate or an honest doc that compatibility is telemetry only.

Required action:
Either make frontend compatibility part of readiness/release gating, or update docs and add another deploy-time compatibility check.

F. Auto-cut scheduler safety requirements

F1. NET-NEW, HIGH, NEW-WORK: the existing green signal is not sufficient for unattended tag creation.

Evidence:
- GitLab release pipeline is tag-only and has no test stage: .gitlab-ci.yml:1-.gitlab-ci.yml:11.
- Gerrit Verified is disabled: .gerrit/project.config:312-.gerrit/project.config:315.
- release_milestone_checker checks develop tip and staging gate statuses: scripts/release_milestone_checker.py:321-scripts/release_milestone_checker.py:374, scripts/release_milestone_checker.py:493-scripts/release_milestone_checker.py:531.

Impact:
A scheduler that creates v* tags when “develop is green” needs a stronger definition than currently exists. The present system can say staging smoke/canary is current, but it does not prove full CI passed for the exact commit.

Required action:
Minimum auto-cut gate should require:
- exact develop commit SHA resolved from Gerrit;
- all Gerrit changes included in the release ticket are merged on develop;
- no open blockers;
- fresh CI test/lint/build success for that exact SHA;
- staging deployed the exact candidate artifact for that SHA/tag;
- canary and smoke records are fresh and match that SHA;
- release bundle/signature/SBOM generation succeeds in dry-run or candidate mode.

F2. NET-NEW, HIGH, NEW-WORK: scheduler must not create a tag until artifact identity is unambiguous.

Evidence:
- staging-sync currently stages raw develop SHA: scripts/sync_staging_to_develop.sh:255-scripts/sync_staging_to_develop.sh:270.
- GitLab publishes only tag/sha-short/latest on v* pipelines: .gitlab-ci.yml:118-.gitlab-ci.yml:120.

Impact:
If auto-cut tags before staging, staging did not validate the exact release tag artifact. If it waits for staging first, current artifacts may not exist. This must be designed explicitly.

Required action:
Use a candidate artifact flow. Examples: build branch SHA images for develop, create rc tags for staging then promote via final tags only after validation, or make the final v* tag trigger build and then stage/prod gates before deployment while accepting that the tag exists before validation completes. Each has different operator semantics.

F3. NET-NEW, MEDIUM, MODIFY: release_milestone_checker can be reused, but its output vocabulary is still old release-cut readiness.

Evidence:
- The checker publishes statuses such as blocked, canary_pending, smoke_pending, ready_for_promote: scripts/release_milestone_checker.py:37-scripts/release_milestone_checker.py:57.
- It asks whether tickets are merged on develop and gates on canary/smoke: scripts/release_milestone_checker.py:443-scripts/release_milestone_checker.py:550.

Impact:
The logic is close to useful, but “ready_for_promote” used to mean ready to create a main promotion change. Under the new model it would mean ready to cut an immutable release tag, a stronger action.

Required action:
Rename statuses or add explicit tag_cut_ready/tag_cut_blocked states, and make the audit payload include exact candidate SHA, candidate artifact identity, and gate freshness windows.

F4. NET-NEW, MEDIUM, NEW-WORK: unattended auto-cut should require a monotonic version allocator.

Evidence:
- backend/agents/auto_tag_release.py currently derives a release branch from the tag and updates release/vX.Y: backend/agents/auto_tag_release.py:104-backend/agents/auto_tag_release.py:108, backend/agents/auto_tag_release.py:193-backend/agents/auto_tag_release.py:241.
- Its CLI takes an explicit --tag and defaults --main-branch main: backend/agents/auto_tag_release.py:295-backend/agents/auto_tag_release.py:303.

Impact:
The old tool is not an auto-cut scheduler. It assumes someone provides the tag and then mutates release branches/main-derived state. A new scheduler must allocate vX.Y.Z safely, avoid duplicates, and refuse to move existing tags.

Required action:
Build a new tag allocator or make version selection explicitly human-provided. Never reuse auto_tag_release.py without deleting release branch updates and main defaults.

G. Other blockers and stale assumptions

G1. PRIOR-KNOWN, HIGH, SUPERSEDE: ADR-0020’s rejected tag-only alternative is now the chosen model.

Evidence:
- ADR-0020 says “Rejected: release = tag only” because main remained load-bearing: docs/adr/ADR-0020-release-cut-as-single-merge-change.md:249-docs/adr/ADR-0020-release-cut-as-single-merge-change.md:255.

Impact:
This is the clearest documentation contradiction. Leaving it as-is will cause future work to defend main as intentional.

Required action:
Write a new ADR that explicitly supersedes ADR-0020 and states why the previous rejection no longer holds.

G2. NET-NEW, MEDIUM, MODIFY: release conductor state machine can stay, but release identity needs to move from branch/release-cut to tag/build provenance.

Evidence:

- The state graph already covers building, staging, canary, done, failed, and rolled_back: backend/release_conductor/state_machine.py:20-backend/release_conductor/state_machine.py:37.

Impact:
The state machine is not inherently main-specific, so deleting it would be overreach. But release_id/version creation and audit fields should bind to immutable tag, commit SHA, image digests, and bundle id.

Required action:
Modify conductor creation/ledger paths to record tag provenance. Keep the state graph unless another audit finds branch-specific assumptions in dispatchers.

G3. NET-NEW, LOW, KEEP/MODIFY: omnisight-main-sync is named “main” but already tracks gerrit/develop.

G4. NET-NEW, MEDIUM, MODIFY: GitLab Container Registry is canonical in docs, but staging and some scripts still assume GHCR or generic registry behavior.

Evidence:
- docs/operations/release-image-pipeline.md says v* tag pipelines publish to GitLab Container Registry: docs/operations/release-image-pipeline.md:48-docs/operations/release-image-pipeline.md:75.
- staging compose defaults to GHCR images: deploy/staging/docker-compose.yml:80, deploy/staging/docker-compose.yml:221, deploy/staging/docker-compose.yml:263.

Impact:
Release artifact verification can pass for one registry while staging/prod pull another registry/tag. This is a classic “green but not the deployed thing” failure mode.

Required action:
Make registry, tag, and digest resolution a single shared contract across GitLab CI, staging, prod deploy, and health/audit output.

G5. PRIOR-KNOWN, HIGH, DELETE: auto_tag_release.py still creates release/vX.Y branches and depends on auto_promote_main.

This cannot be salvaged by changing one default. Its core behavior is branch maintenance that the new plan rejects.

Required action:
Delete or replace with a tag-only implementation that does not import auto_promote_main, does not update release/v*, and refuses to operate except on develop commits.

Minimum acceptance checklist for the migration

- No service/timer/script can push refs/for/main or update release/v*.
- Production deploy refuses main, release/*, hotfix/*, and any non-v* branch ref.
- Staging and production pull the same registry namespace and immutable tag/digest scheme.
- An exact develop commit can be proven green before any final production tag is created, or the process explicitly treats final tags as post-build candidates until gates pass.
- Feature flags have a frontend-safe runtime API, client provider, fail-closed semantics, and type alignment.
- Supply-chain audit truthfully reflects the actual signing mode and final image digests.
- ADRs and operator docs make the new trunk/tag model normative and mark old main/release-cut decisions superseded.
