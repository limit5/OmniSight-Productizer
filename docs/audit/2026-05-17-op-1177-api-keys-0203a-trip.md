# OP-1177 — `api_keys` duplicate that trips `_backfill_api_keys` on `idx_api_keys_lookup`

## TL;DR

The two rows the ticket points at are **duplicate API keys** in the
semantic sense — they encode the **same legacy bearer secret** — and
the migration trips because one row is already in the post-migration
state (`key_lookup_index` populated) while the other is still in the
pre-migration state (`key_lookup_index` NULL, `key_hash` is the bare
sha256 hex). When `_backfill_api_keys` reaches the second row, the
UPDATE writes `key_lookup_index = <bare sha256>`, which collides with
the first row's already-populated `key_lookup_index` on the unique
index `idx_api_keys_lookup`.

Identity proof (sha-prefix arithmetic, no PG access needed):

| Row label | Distinguishing field | Value                                                              | Notes                                                       |
|-----------|----------------------|--------------------------------------------------------------------|-------------------------------------------------------------|
| A         | `id`                 | `ak-legacy-31be6f6c8763`                                           | Task-#106 deterministic id, stem = `sha256(legacy)[:12]`    |
| B         | `key_lookup_index`   | `31be6f6c8763e7d02a2428015fdb00b6c7f559146f5645492829a667a319e26c` | Full 64-char `sha256(legacy)`; **starts with** `31be6f6c8763` |

`A.id_stem (31be6f6c8763) == B.key_lookup_index[:12] (31be6f6c8763)` ⇒
**same `sha256(legacy_secret)` ⇒ same underlying bearer**.

## How `_backfill_api_keys` trips (code path)

`backend/alembic/versions/0203a_kse_envelope_credential_backfill.py`
lines 119–161. Re-read here for clarity (read-only audit per the ticket
scope):

```python
def _backfill_api_keys(conn) -> tuple[int, int]:
    rows = conn.exec_driver_sql(
        "SELECT id, COALESCE(tenant_id, 't-default') AS tenant_id, "
        "key_hash, key_lookup_index FROM api_keys"
    ).fetchall()
    for row in rows:
        key_id, tenant_id, key_hash, lookup = row
        ...
        if _looks_like_carrier(key_hash):
            if not lookup:
                lookup = _token_from_binding(_unpack_ks_payload(key_hash))
                UPDATE api_keys SET key_lookup_index = :lookup WHERE id = :id
            else:
                skipped
            continue
        packed = _pack_ks_payload(_binding_payload(key_hash, ...), ...)
        UPDATE api_keys
           SET key_hash = :packed,
               key_lookup_index = :lookup   # :lookup = OLD key_hash (bare sha256)
         WHERE id = :id
```

Key observations:

1. The UNIQUE constraint that fires is `idx_api_keys_lookup` —
   created by `_ensure_lookup_columns` (line 107–110) at the start of
   the same migration. It's a *unique* index on `key_lookup_index`
   (also already present in `backend/db.py:1342-1343` for the SQLite
   bootstrap CREATE TABLE path).

2. The migration writes `key_lookup_index = <bare sha256>` in **two
   branches**:
   - carrier-with-NULL-lookup branch (line 137–143): writes the `tok`
     extracted from the carrier binding payload. By the binding
     contract that `tok` IS the bare sha256 hex of the legacy secret.
   - legacy-plaintext branch (line 153–159): writes the *old*
     `key_hash` literal — which, in the K6 contract for `api_keys`,
     is exactly the bare sha256 hex of the secret.

3. Both branches therefore converge on the same value when two rows
   encode the same secret: `sha256(legacy_secret)`. That value is
   `31be6f6c8763e7d02a2428015fdb00b6c7f559146f5645492829a667a319e26c`
   for this incident.

4. Whichever of {A, B} is processed second collides with whichever
   was processed first. Alembic runs the loop inside a single
   transaction, so the trip aborts the whole migration; the row that
   "looks" already-migrated did *not* persist its update from this
   run — it was either (a) populated by application-side code at
   create-time, or (b) populated by an earlier, partially-committed
   admin action. (b) is consistent with the operator-side cleanup
   pattern noted in `L-OP-1176`.

## Why two rows exist for one secret (chronology hypothesis)

The lesson `docs/sop/lessons/L-OP-1176-prod-alembic-drift-hidden-by-livez-routing.md`
(line 64) explicitly calls out the cleanup pattern that produces
exactly this duplicate:

> Cleanup duplicate `api_keys` rows (the migration 0203a_kse trips on
> `idx_api_keys_lookup` unique-constraint conflicts) — keep the
> canonical `ak-legacy-<sha256(legacy_secret)[:12]>` form, delete the
> pre-Task-#106 UUID-derived legacy stub.

Backing context in the K6 code, `backend/api_keys.py:288-340`
(`migrate_legacy_bearer`) and the regression guard
`backend/tests/test_api_keys_legacy_migration.py`:

- Pre-Task-#106 (≤ 2026-04-20): `migrate_legacy_bearer` generated a
  fresh `ak-<uuid.uuid4().hex[:10]>` id per call. Two uvicorn workers
  with `OMNISIGHT_DECISION_BEARER` set both raced through `INSERT`
  with **different** uuids → no UNIQUE collision on `id` → **N rows
  per single secret** in prod. Multi-worker regression filed as the
  smoke finding under SP-4.6.

- Task-#106 fix (2026-04-21, `api_keys.py:294-297` doc): `key_id =
  f"ak-legacy-{hashed[:12]}"` + `INSERT ... ON CONFLICT (id) DO
  NOTHING` ⇒ workers all converge on **one** deterministic id.
  Existing pre-#106 rows are **not** deduped by this change — it
  only stops *new* duplicates.

So in prod, for any single value of `OMNISIGHT_DECISION_BEARER` that
was first migrated on multi-worker pre-2026-04-21 code and then
booted again post-2026-04-21, the table can hold:
- one **canonical** row: `id = ak-legacy-<sha[:12]>` (Task-#106 form),
- one or more **stub** rows: `id = ak-<random-uuid-hex>` (pre-#106 form).

Row A (id `ak-legacy-31be6f6c8763`) is the canonical row. Row B (id
unknown from the ticket text, but distinguished by its already-
populated lookup) is consistent with the pre-#106 stub form.

## Are they duplicates? (the ticket's question)

**Yes.** Forensic proof in three independent lines:

1. **Hash arithmetic.** Row A's id stem `31be6f6c8763` ≡ first 12 hex
   chars of Row B's `key_lookup_index`
   `31be6f6c8763e7d02a2428015fdb00b6c7f559146f5645492829a667a319e26c`.
   Per `api_keys.py:317-318`, the canonical id stem is *defined* as
   `hashlib.sha256(legacy_secret).hexdigest()[:12]`. Per K6's
   `_hash_key` (`api_keys.py:106-107`) and `_backfill_api_keys`'s
   `:lookup` value (line 158), `key_lookup_index` *is*
   `hashlib.sha256(legacy_secret).hexdigest()`. Same prefix ⇒ same
   sha256 ⇒ same legacy_secret (sha256 is preimage-resistant; for
   *non-adversarial* legacy_secret values the collision probability
   is ≈ 2⁻²⁵⁶, indistinguishable from identity).

2. **Code path.** Both rows can only arrive at this lookup value
   through `migrate_legacy_bearer` (or its pre-#106 ancestor) writing
   `sha256(OMNISIGHT_DECISION_BEARER)`. No other code path in
   `backend/api_keys.py` produces the `legacy-bearer` name + sha256-
   prefixed id combo.

3. **Operational context.** `L-OP-1176` documents the exact failure
   mode and exact cleanup ("keep canonical, delete pre-#106 stub"),
   strongly implying prior observation of the same duplicate-secret
   pattern in prod.

## Is one already-migrated and the other in-process?

**Yes — and the two questions are not exclusive; both are true.**

- Row B (already-migrated): `key_lookup_index` is populated with the
  bare sha256 hex. The migration's "carrier-with-NULL-lookup" branch
  treats such a row as `skipped` on subsequent runs.
- Row A (in-process / would-be-migrated): on the migration's pass,
  `_backfill_api_keys` reaches Row A, attempts to populate
  `key_lookup_index` with the same sha256 value, and trips on the
  unique index established earlier in the same migration. The whole
  migration aborts; Row A stays in its pre-migration state.

Whichever of A/B was processed first by the loop is irrelevant — the
collision is symmetric. What matters is that **two rows share the
same secret content while only one of them is in the post-migration
form at the time `_backfill_api_keys` runs.**

## Recommended cleanup (out of scope for this ticket — db area)

Per `L-OP-1176`: keep the canonical Task-#106 row, drop the pre-#106
UUID-id stub:

```sql
BEGIN;
-- 1. Confirm only one secret is involved (the pre-flight sanity check).
SELECT id, key_lookup_index, key_hash IS NOT NULL AS has_hash
  FROM api_keys
 WHERE id = 'ak-legacy-31be6f6c8763'
    OR key_lookup_index = '31be6f6c8763e7d02a2428015fdb00b6c7f559146f5645492829a667a319e26c';
-- 2. Delete the pre-#106 stub (the row whose id does NOT start with 'ak-legacy-').
DELETE FROM api_keys
 WHERE key_lookup_index = '31be6f6c8763e7d02a2428015fdb00b6c7f559146f5645492829a667a319e26c'
   AND id NOT LIKE 'ak-legacy-%';
-- 3. Re-run 0203a_kse_envelope_credential_backfill. The remaining row
--    is the canonical Task-#106 form; the migration's carrier branch
--    will idempotently noop or populate the lookup as appropriate.
COMMIT;
```

That cleanup touches DB rows and must be filed as a separate ticket
in the `db`/`devops` area (this ticket's area is `backend, docs`
only — per the runner-side capability matrix, I am explicitly
prohibited from altering DB state from this pickup). The findings
above are sufficient to scope that follow-up ticket.
